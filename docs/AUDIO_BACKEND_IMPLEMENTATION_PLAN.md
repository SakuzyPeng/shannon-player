## 工程结构

引擎独立为 cargo workspace 成员，与 Tauri 壳解耦。仓库现状是 workspace 成员平铺在
根目录（`core/`、`src-tauri/`），新成员沿用同一布局，不引入 `crates/` 前缀——
`core/src/model.rs` 的 ts-rs `export_to` 是相对路径，搬动目录层级会切断前后端契约链路，
而目录前缀本身不产生工程价值：

```text
src-tauri/           Tauri 壳：commands、事件桥、窗口（现状）
core/                曲库：扫描、探测、稳定 ID、元数据覆盖（现状，crate 名 shannon-core）
audio/               播放引擎：解码、PCM 管线、输出后端，零 Tauri 依赖（新增，shannon-audio）
import/              链接导入 ImportService（后期，shannon-import）
```

- `shannon-audio` 不依赖 Tauri，验收条件中的 gapless、seek、欠载压测才能以
  `cargo test` 无头执行。
- 引擎附带 example 级开发 CLI（如 `cargo run -p shannon-audio --example play <file>`），
  属于架构约束允许的开发期诊断工具，不进入正式播放路径。
- `src-tauri` 只保留胶水：命令转发、事件转发、状态桥接，不写音频逻辑。

## 引擎线程模型

控制面与数据面分离：

```text
Tauri command ──PlayerCmd──> 控制线程（状态机唯一所有者）
                                 |  管理 current / next 两个源
                                 v
              解码工作线程 ──> 无锁 SPSC 环形缓冲 ──> 输出回调
                                                        |
              控制线程 <── 无锁事件队列（切歌边界、欠载等标记）
                 |
                 v
       对外事件：Progress / TrackChanged / StateChanged / Error / DeviceListChanged
```

- 控制线程是 `Idle / Loading / Playing / Paused / Error` 状态机的唯一所有者，经消息
  通道接收命令。Tauri command 只投递消息并立即返回，结果一律走事件，音频不进入
  Tauri 的 async 运行时。
- 解码工作线程串联容器读取、解码与 PCM 管线，向环形缓冲推入帧。
- 输出回调只从环形缓冲消费；越过切歌边界、发生欠载等时刻仅向无锁事件队列压入标记，
  对外事件统一由控制线程消费标记后发出。

**阶段 0 把控制与解码合成了一个线程**（实现见 `audio/src/engine.rs` 的模块文档）：
循环内先收干净命令再喂料，命令响应延迟等于一批解码的时间（几毫秒）。这不触碰任何
架构不变量——输出回调仍然只消费环形缓冲——而拆分所需的两线程 generation 同步与 seek
三方握手，在阶段 0 没有对应收益。真正需要独立解码线程的是 next 曲目预解码与 current
并行，即阶段 1 的 gapless，届时按上图拆分。

实时纪律清单（细化架构约束实时链路不变量第 3 条）：

- 回调可触碰的共享结构仅限：SPSC 消费端、原子量（音量、静音、generation、欠载计数）、
  无锁事件队列的生产端。
- 回调内禁止 Mutex（包括“只锁一瞬”）、文件与网络 I/O、动态分配、格式化日志。
- 欠载计数为原子累加，经 stats 查询接口暴露，对应架构约束验收条件第 5 条。

seek 与切歌沿用研究笔记的 generation 方案：控制线程递增原子 generation，解码线程丢弃
在途数据、清空环形缓冲并从新位置重填，达到预缓冲阈值（沿用概念验证的 300 ms）后恢复
消费。

generation 解决音频数据的新旧，不解决命令与事件的配对：seek 等异步命令另携带自增
request_id，进度与完成事件回带 generation 与最近 request_id，前端据此丢弃过期回报，
避免连续拖动进度条时旧回报把界面拉回旧位置。队列侧的对应机制是 queueRevision，见
「队列归属与切歌交接」。

丢弃过期回报只适用于进度这类会被新值持续覆盖的标量状态；`TrackChanged` 这类描述
已发生迁移的事件是事实，只能对账、不得丢弃，规则见「队列归属与切歌交接」。

## 播放位置与进度事件

- 播放位置 = 输出回调累计消费帧数 − 输出设备延迟，符合架构约束不变量第 6 条，
  不以 JavaScript 定时器为事实来源。
- 进度事件按约 5 Hz 推送；UI 在事件间用 requestAnimationFrame 插值，事件只做重锚定。
- 歌词逐字同步必须使用扣除设备延迟后的位置。共享模式输出延迟普遍达数十毫秒，
  不补偿会让逐字高亮系统性偏早。

## 队列归属与切歌交接

**现状：已落地**（`audio/src/ring.rs` 的边界打点与截断、`audio/src/engine.rs` 的
`head` / `sounding` / `staged` 三态、`src/hooks/useSyncNext.ts` 与 store 的 `nextHandoff`）。
本节除下列几处外描述的都是已实现行为：

- **`set_next` 之外还有一条路**：「下一首」同时可以随 `Load` 原子下发，而且前端**必须**
  这么做。理由与音量、初始位置完全相同——命令跨 IPC 的到达顺序没有保证，而显式装载会
  清掉待接续的下一首（它属于上一个处境）。只用 `set_next` 的话，晚到的被清、早到的被
  抹，两种顺序都可能，表现出来就是「无缝换曲时好时坏」。
- **后续 `set_next` 同时携带播放链 ID 与 queueRevision**。播放链 ID 只在显式 `Load`
  时变化，gapless 交接沿用同一条链：旧链迟到的更新因此不能越过新 `Load`；同链内则只
  接受更大的 revision。更新若先于对应 `Load` 到达，按链暂存并在装载时合并，不能简单
  丢掉——否则只是把“晚到覆盖”修成了“早到丢失”。Tauri 外壳遇到这种更新时会先创建
  控制线程再投递；输出设备依旧到 `Load` 才打开，不会为暂存 next 提前占用声卡。
- **控制线程与解码线程仍未拆开**。原设计说 gapless 需要 next 与 current 并行解码，
  实测不需要：环形缓冲有一秒半的余量，交接只是「同一个循环里换个音源继续写」，唯一的
  阻塞动作（打开下一首的文件）挑在缓冲喂满、控制线程本来就要休息的时刻做。
- **整条输出流的采样率由第一首协商决定**，后续曲目重采样到它上面。反过来（每首按自己
  的采样率重开设备）能省掉这级转换，但换曲必然有停顿——两者不可兼得，此处取「无缝优先」，
  且转换会如实记进 stats。
- 作废的打点**不回收**：回退打点写下标会与消费端正在读的槽位打架。它留在原地并与新打点
  落在同一个绝对下标上，两者一起被越过，哪一条该发事件由生产端自己记。

队列权威保留在前端 Zustand store。引擎侧建模为三态：**解码头**（正在往缓冲里写的那首）、
**正在发声的那首**（消费端越过边界才推进）、**已备好的下一首**。前两者的区分是必须的——
解码领先播放最多一秒半，混作一谈就会让界面提前一秒半切歌、让拖动进度条定位到下一首上。

阶段 0 已有统一后继计算：`shuffleOrder` 保存一次洗好的 uid 排列，`next()`、`prev()`、
队列面板与队列增删改都消费同一顺序；repeat 语义也共用一套计算。当前曲目自然结束后由
前端装载下一首，尚无 next 槽位或预解码 PCM，因此此时引入 queueRevision 没有可失效的
对象。下面从 `set_next` 起的协议随阶段 1 一起落地：

- store 在每次队列、循环或随机状态变化时重算下一首，并调用
  `player_set_next(chainId, queueRevision, next)`；`next = null` 也是一条完整更新，表示
  当前曲目放完就停。
- store 每次队列相关变更递增 queueRevision；引擎记录最近收到的值，并在
  `TrackChanged { fromUid, toUid, queueRevision }` 中回带。
- queueRevision 必须使已预解码的旧 next 音频在边界前失效，二选一实现：next 使用
  独立的可替换预缓冲，替换时整体丢弃旧 next（主缓冲只含 current，旧缓冲由解码或
  控制线程回收，释放不得发生在回调内）；或 PCM 块携带 revision，消费端在边界处
  校验并拒绝消费过期块。无论何种实现，输出端绝不能消费过期 revision 的 next
  PCM——否则改队列对听感无效，用户仍会听到旧队列的下一首。
- 边界到达而新 next 尚未达到预缓冲阈值时，走 seek 的再缓冲路径（短暂停顿后续播）：
  宁可出现可解释的停顿，不播放过期音频。
- revision 的全部过滤职责都在边界之前。已越过边界的切歌是既成事实，`TrackChanged`
  一经产生，引擎与前端都不得因 revision 过期而丢弃：边界先于改队列发生时（事件仍
  在途中，store 已升至 R+1），revision R 的 TrackChanged 描述的正是当前真实发声的
  曲目，丢弃它会让界面停留在旧曲，造成另一个方向的音频与界面分裂。由于 PCM 失效
  约束已保证过期 next 不会发声，“按旧队列错误切歌”不需要靠丢事件防御。
- 前端对 `TrackChanged` 做对账，而非按 revision 相等校验：以 toUid 在当前队列中
  定位并设置 currentIndex（不做下标递增）；toUid 已被新队列移除时，以“正在播放但
  不在队列”的事实状态呈现，是否自动跳到新队列应播曲目由产品层显式决定，协议不
  静默处理。前端保留一个有界 handoff 历史，并按事件自身的 `(loadId, queueRevision)`
  认领队列项；只看“此刻最新的 next”会把迟到的 B 事件误映射成后来指定的 C。对账后
  一律按当前队列重算 next 并重发 `set_next`；回带的 revision 用于识别该次切歌依据的
  队列版本。
- revision 的失效性只作用于尚未消费的 next PCM；current 的 PCM 不因改队列失效，
  仅由 seek 与切歌的 generation 控制；已消费发声的音频不受任何标识追溯。
- 引擎在边界处帧级精确续播（满足不变量第 7 条的 gapless 要求）。实测：把一段连续扫频
  切成两个文件接续播放，接缝前后各 200 帧与未切开的原信号**逐样本一致**；真实设备上
  三段 6 秒 FLAC 连播，消费帧数合计正好等于三段之和，欠载 0 次。
- 应用内实测（驱动 Tauri 原生窗口，走真实 CPAL 输出）。上报的位置来自输出回调已消费的
  帧数，所以它能反映消费有没有停过；界面上的秒级读数不够分辨，改按进度条填充比例取亚秒
  位置（一像素约 47 ms）。边界前后各自线性外推得到的交接时刻相差 **28 ms 与 50 ms**，
  都小于该测法的分辨率，相邻采样之间没有任何平台期——重开设备并重填缓冲是几百毫秒量级，
  落不进这个范围。注意它证明的是「消费未中断」，**逐样本连续仍由上面那条无头断言负责**。
  同一队列 12 首（FLAC / ALAC / WAV / AIFF / CAF / AAC / MP3 / Vorbis / 48 k / 96 k /
  24 bit）无人值守连播到底并在队尾停下，播放条的标题、时长、位置随交接更新且传输状态
  不抖动。在当前曲目只剩约 1 秒时改「下一首是谁」两个方向都即时生效：切成单曲循环则同
  一首重新开始、已预解码的下一首一个样本未出，切回顺序则接上重新指定的那一首——这个时
  机走的正是「消费端配合截断」，不是「还没排上就换掉」。
- repeat-one 即 `set_next` 指向当前曲目自身。
- `TrackChanged` 必须在消费端越过边界帧时判定，而不是解码器切源时——解码可领先播放
  数秒，按解码时机发事件会让界面提前切换曲目信息。实现上在环形缓冲维护
  (generation, queueRevision, 边界帧号) 标记队列；输出回调越界时仅向无锁事件队列
  压入标记，由控制线程消费后对外发事件——标记代表已发生的越界消费，一律发出，
  不做 revision 过滤；回调自身不做任何事件发送。

后期曲库与队列若整体下沉 Rust，再重估队列归属；当前阶段不做该迁移。

## 输出端点切换

**现状：已落地**（`output/mod.rs` 的 `DeviceInfo` / `DeviceEnumerator`、
`output/cpal_out.rs` 的 `CpalDevices`、`engine.rs` 的 `switch_device`、外壳的
`player_list_devices` / `player_set_device`、前端 `hooks/useSyncDevice.ts` 与设置页
「输出设备」行）。设计要点如下，均对应架构约束不变量第 8 条「必须进入显式状态机，
不能静默改用不同质量的输出路径」。

- **端点身份用 cpal 的 `DeviceId`**（macOS 上是 CoreAudio 的设备 UID，跨重启与重新
  插拔稳定），不用设备名——同型号的两只 USB DAC 名字一模一样，按名字选会随机命中。
  按名字片段匹配只保留给 `play --device` 那条诊断路径。挑不到指定的那台一律报错，
  **不回落默认**。
- **枚举与切换分开建模**。枚举是查询（`DeviceEnumerator`），不进引擎的串行命令队列、
  也不因此创建引擎；切换是命令（`PlayerCmd::SetDevice`），要动输出链路。菜单每次
  展开都重新枚举；列表**不按能力筛**，用不了的端点选中后给一句明确的能力错误，
  比让它在列表里凭空消失更容易理解。
- **先预检再拆流**。`negotiate` 只预演不碰设备，失败时旧流仍在正常发声，此时保持原状
  并回一条 `DeviceRejected`。它与 `Error` 是**两个**事件：后者的含义是播放链已经拆掉，
  用它报换设备失败会让界面显示成已停止而用户耳朵里音乐还在响。什么都没在放时同样
  预检（用标称 44.1 kHz 去问），否则错误要等到用户下次按播放才冒出来。
- **选择与回执都带 `deviceRevision`，按 latest-wins 对账**。Tauri 命令会并发抵达，用户
  快速点 A → B → C 时不能拿控制线程的收件顺序冒充点击顺序；引擎丢掉旧 revision，前端
  也丢掉迟到回执。拒绝事件同时带回引擎真正保留的偏好，界面据此回滚，不能拿一格本地
  点击历史猜。自然结束则同步收束传输意图，结束后换端点仍保持 `Ended`，不会重放尾巴。
- **换端点不是新装载**。曲目、队列位置与待接续的下一首都要活过这次换流，因此不能用
  `teardown`（那是显式装载的语义）。解码头可能已经跑到下一首——那一步已经清掉了
  `next_request`，要在丢弃 head 前按 `load_id` 判出它是未来那首并退回待接续槽。
- **接回来的位置取 `played_frames`（已发声）而不是已消费**：两者差一个设备延迟，
  共享模式下普遍数十毫秒，按已消费接会跳过那一截还没进耳朵的音频。
- **偏好落在 `ui-settings.json` 且连设备名一起存**。设备可能不在了，只存标识的话界面
  只能显示成「系统默认」，用户既看不出偏好还在、也无从理解为什么下次插回去声音又
  自己跑过去了。不在时保留偏好但**不下发**（否则每次启动都弹一句他没做过任何操作的
  提示），界面标成「（当前不可用）」。菜单还要把用户偏好、系统默认端点与引擎实际
  输出端点分开标注；三者在切换途中或设备缺席时完全可能不同。
- **热插拔跟随不做**。架构约束把「平台特有的设备热插拔、默认设备角色和错误恢复策略」
  列为不能假设 CPAL 已提供的能力；当前设备在播放中消失走的是 CPAL 错误回调 →
  结构化 `Error`，不静默恢复。

## 解码管线

架构约束分层图中 `SymphoniaDecoder` 与 `CodecSpecificDecoder` 的落地形态合并为一条
Symphonia 管线加自定义解码器注册：

- 容器探测、解复用、元数据、seek 统一走 Symphonia；Opus 等其尚未覆盖的编码以自定义
  Decoder 注册进 CodecRegistry，复用其 MKV/WebM/Ogg 解复用器，不另起容器解析栈。
- Opus 解码采用 libopus 绑定（`opus` / `audiopus` 选型时定），seek 需处理 pre-roll。
- 该方案与架构约束“解码后端选择”第 3 条一致，是专用进程内解码器的具体集成方式；
  后端分类实际收敛为三类：Symphonia（含插件解码器）、可选 libav、原生空间。

数据契约：

- 全链交换格式为 f32 交错 PCM，以每声道时间帧计数（不变量第 1 条）。
- 源规格自解码起点即携带 `layout` 与 `layout_source`（显式标签 / 声道数推断 / 默认），
  对应固定多声道笔记对布局置信度的要求；溯源事后补录代价大，必须一开始就进类型。

管线顺序：

```text
解码 -> gapless 裁剪 -> ReplayGain -> 重采样 -> 声道映射 -> 环形缓冲 -> (输出回调) 音量
```

两处与原设计不同，都是实现时想清楚的：

- **音量挪到了输出回调**，不在解码管线里。管线可以领先播放一秒半，在那儿改增益意味着
  用户按下静音后还要等一秒半才听见变化；暂停的淡出同理，必须由回调驱动才能即时。
  ReplayGain 是每首歌一个常数，留在管线里没有这个问题。
- **重采样在声道映射之前**，即按**源**声道数重采样：单声道上混后再重采样等于把同一条
  声道算两遍。这个顺序在多声道路径上同样成立——那条路径把布局原样交给系统，声道数
  自始至终不变，不存在「先降到 2 路再重采样更省」的选项（下混是系统的事，见下）。

各级的实现要点：

- gapless 裁剪使用容器与码流提供的 encoder delay/padding（Symphonia 的
  `enable_gapless` 或等价机制）。
- 音量在引擎内做线性增益，变化带 10–20 ms 斜坡；不做斜坡会产生可闻爆音，斜坡行为
  纳入验收。
- 暂停 = 斜坡到零后回调停止从环形缓冲取帧，但继续向设备写零帧，输出流与设备时钟
  保持活跃；只有停止播放或设备切换才拆除输出流。直接停掉回调消费会让恢复播放经历
  设备重启延迟，也让基于消费帧数的位置时钟失去参照。
- 重采样用 rubato 的 `Fft`（同步 FFT）而非异步 sinc：播放期的比率是**固定**的，
  同步重采样器为此而设计，同等质量下开销更低；可变比率能力在这里用不上，
  变速播放才需要换成可调比率的实现。仅在源采样率不等于设备采样率时启用，
  并在 stats 中如实标记“已重采样”，对应架构约束对 bit-perfect 措辞的限制。
  实测开销：44.1 → 48 kHz 立体声，release 构建下播放 10 秒耗 0.12 秒 CPU（约 1.2%）。

## 响度归一化（ReplayGain 2.0）

**现状：已落地**（`audio/src/loudness/`：`mod.rs` 测量、`store.rs` 存储、`service.rs` 队列与
worker、`qos.rs` 后台优先级；外壳在 `src-tauri/src/loudness.rs`，前端顺序在
`src/hooks/useLoudnessQueue.ts`）。本节除下列两处外描述的都是已实现行为：

- **专辑增益仍未提供**（见「产品契约」末条），只做逐曲增益。
- **并发度仍是 1 个 worker**，提高默认值的前提条件未变（目标平台重跑 `--loudness`
  的 1/2/4/8 线程 + 同时跑欠载测试）。「现在全部分析」这个意图级动作也尚未做成入口
  ——当前等价于「打开开关」，队列本来就是整库。

QoS 三平台的验证程度不同：macOS 有运行时读回校验，Windows / Linux 只做了 FFI 签名的
交叉编译检查（且 `cargo check --target x86_64-pc-windows-msvc` 目前卡在 cpal 0.18.1 与
windows-core 0.62 不兼容，与本功能无关，但意味着 Windows 侧当前整体不可构建）。

### 标签靠不住，必须自己算

实测本机曲库 954 首：带 `REPLAYGAIN_TRACK_GAIN` 的 **0 首**，带 `R128_TRACK_GAIN` 的
**0 首**。这不是个例——该库 87.5% 是 ALAC，多数经 Apple Music / iTunes 链路导入，
而那条链路从不写 ReplayGain 标签（Apple 自己用 Sound Check，同样是自己算，
只是把结果留在自家数据库里）。

因此**读标签只能作为可选的加速路径，不能作为实现方案**：只读标签的 ReplayGain
在这个库上覆盖率为零，做了等于没做，且与「阶段 2 补齐探测」无关——标签读得再干净
也读不出不存在的东西。

推论：本功能自带输入产出能力，**不依赖阶段 2 的扫描器补齐**，可独立排期。

### 测量用 `ebur128`，不自己实现

选定并锁定 [`ebur128`](https://crates.io/crates/ebur128) 0.1.10（MIT，与
AGPL-3.0-only 兼容），启用 `precision-true-peak`：

- 纯 Rust（仓库内的 C 头文件只服务于反向的 `capi` 导出，不构成 C 依赖），不影响交叉编译；
- 带 `c-tests` / `reference-tests` feature，对照原版 libebur128 逐值验证，
  这比我们自写的任何测试都硬；
- API 与现有管线对齐：`add_frames_f32` 直接吃交错 f32，`loudness_global` 出 LUFS，
  `true_peak` 出真峰值（防削顶用）。实际只开 `Mode::I | Mode::TRUE_PEAK`，不为用不到的
  momentary / short-term / LRA 付成本。

K 加权滤波系数、-70 LUFS 绝对门限与相对门限那套是标准写死的，自己实现没有差异化
价值：写对了跟库一样，写错了只有听感会告诉你，而那时全库已经分析过一遍了。

### 产品契约：目标、峰值保护与退化

这里采用面向音乐播放的
[**ReplayGain 2.0**](https://wiki.hydrogenaudio.org/index.php?title=Revised_ReplayGain_specification)
目标，不是广播交付的 EBU R128 目标；-18 LUFS 来自该规范，-1 dBTP 是本项目为后续转换
保留的安全余量。常量与公式固定如下，不能只把 `loudness_global` 的结果交给实现者临场决定：

```text
TARGET_LUFS = -18.0
TRUE_PEAK_CEILING_DBTP = -1.0

requested_gain_db = TARGET_LUFS - integrated_lufs
peak_safe_gain_db = TRUE_PEAK_CEILING_DBTP - true_peak_dbtp
applied_gain_db = min(requested_gain_db, peak_safe_gain_db)
linear_gain = 10 ^ (applied_gain_db / 20)
```

- 只施加一个**整曲常量增益**，不上 limiter、不压缩动态范围。若一首安静但峰值很高的曲目
  无法在不削顶的前提下到达 -18 LUFS，就少加增益；「绝不削顶」优先于「一定到目标」。
- `true_peak` 返回线性幅度，每声道取最大值后用 `20 * log10(peak)` 转成 dBTP；
  -1 dBTP 还给后续重采样和设备转换留一档余量。
- `loudness_global` 为 `-inf` / `NaN`（全静音、短于首个 400 ms 门限块等）时标为
  `unmeasurable`，应用 0 dB，并缓存这个结论，避免每次播放都重试。
  实测 250 首中有 10 首落进这一档，**全部是 Logic Pro 采样库里的单周期波形与打击乐
  短音**（单个波形周期只有几毫秒，远短于门限块）；239 首真实音乐无一不可测。
  也就是说这一档在正常曲库里几乎不触发，它防的是**扫描范围混进了音源素材**——
  参见下面「分析队列的输入边界」。
- 首版界面承诺的是**逐曲增益**（`settings.loudnessDesc`），因此只应用 track gain。
  album gain 要先定清播放模式和聚合边界；届时需以 ReplayGain 2.0 的整张合并结果为参照做
  交叉测试，不能仅凭 `loudness_global_multiple` 的函数名就断言任意分块方式等价。

### 声道映射：显式给，不用库的默认猜测

`EbuR128::new(channels, …)` 会按声道数给默认布局，这与本项目「位掩码是权威、未知不猜」
冲突。每个实例创建后必须调用 `set_channel_map`：

- 单声道设为 `DualMono`：当前播放路径会把它复制到左右两路，测量也按实际的双扬声器能量计；
- 常规立体声明确设为 `[Left, Right]`；
- 其它布局在阶段 1 记为 `unsupportedLayout`，不归一化、不假装已分析。阶段 5 接平台多声道
  后，再从 `ChannelLayout` 位掩码逐位置映射；LFE 映射为 `Unused`，未知离散声道仍拒绝猜测。

分析吃的是解码后的**源采样率、源声道布局** PCM，与 ReplayGain 在重采样前应用相呼应；
不得拿输出设备协商后的立体声去反推源布局。

### 分析形态：优先级队列，不是批量全扫

**批量思维是错的**，因为它把成本表述成「用户要等多久」，而那个数字在不同机器上
差一个数量级，没法预告（本机 131 秒的活，老双核笔记本可能是 20 分钟）。

正确的约束不是「全库总时间」，而是「**单首是否快于实时播放**」：

| 量 | 实测值 |
| --- | --- |
| 单首 ALAC（4 分钟）纯解码 | 约 0.4 秒（单线程独占）／约 1 秒（并行下） |
| 可复现歌单全部 11 格式，完整响度分析 | 669× 实时（单线程总体） |
| **真实曲库 250 首，完整响度分析** | **383× 实时**（单线程），其中 ALAC 378× |
| 同批曲目纯解码 | 556× 实时（单线程） |

完整分析比纯解码慢 **1.45 倍**（真实曲库），不是同源歌单测出的 2.4 倍——那份歌单里
PCM 占比高、解码近乎免费，放大了分析的相对开销。**混合负载的比值取决于编码构成，
换个曲库就不一样，因此这个倍数只能用来判断量级，不能当常数**。

纯解码的 0.4 秒不能冒充完整分析，但补测后当前机器仍有两个数量级余量。老机器的余量
不靠猜「慢多少倍」，而靠优先队列尽早预取；若实测落后于播放，影响的是未命中的曲目暂不
归一化，不允许反过来阻塞播放。

顺带测出该功能的存在理由：同一批 239 首真实音乐的 integrated loudness 跨度是
**-29.6 到 -3.2 LUFS**，即 26 LU。不做归一化时，切歌的音量落差就是这个数量级。
对应的应用增益范围 -14.8 到 +7.0 dB——**有曲目需要提升**，因此增益不是单向衰减，
峰值保护那一支必须存在。

于是「预取」与「全库分析」合并为同一件事——一个按播放顺序排优先级的分析队列：

- 优先级 = 距当前播放位置的远近；队列变化（切歌、改队列、开随机）时重排；
- 首版让后台分析器独立解码，**不把 K 加权和真峰值扫描塞进播放生产线程**；只有完整分析
  与欠载共存的测试通过后，才考虑复用播放 PCM 这一优化；
- 后台线程池从队首消费，跑完即全库分析完成——它不再是一个需要用户点的按钮，
  只是「队列跑空」这个状态；
- 跳到队列中段不再是特例，那一段大概率早已算过。

### 并发度：先用一个后台 worker，完整基准后再提高

此前的实测加速比（M4 Pro，8 P 核 + 4 E 核，150 首样本）实际测的是**纯解码**：

| 线程 | 吞吐 | 相对单线程 | 边际 |
| --- | --- | --- | --- |
| 1 | 556x | 1.00x | — |
| 2 | 1128x | 2.03x | +103% |
| 4 | 1902x | 3.42x | +69% |
| 8 | 2360x | 4.24x | +24% |
| 12 | 2715x | 4.88x | +15% |

这张表只能回答解码器如何扩展，**不能**证明 EBU R128 + true peak 的吞吐与播放共存。
`true_peak` 在常见采样率下还要做 4× 过采样，不能写成「多一遍 K 加权、成本接近零」。
现已给 `bench_decode` 增加 `--loudness`：它按本节的 Mode、声道映射、目标和峰值保护跑完整负载。

用仓库可复现的 11 格式实测歌单（同一源、总长 7.3 分钟）做 sanity check：单线程纯解码
1628× 实时，完整响度分析 669× 实时，墙钟成本约为前者的 **2.4 倍**。样本太小且都来自
同一源，足以证明「两种负载不能混用」，不足以据此选全平台并发度。

因此阶段 1 先用 **1 个后台 worker**，并标记为后台 QoS（macOS `QOS_CLASS_BACKGROUND`，
Windows `THREAD_MODE_BACKGROUND_BEGIN`，Linux nice + ioprio）。它已经足以沿播放顺序预取，
也不会拿未经验证的并发结论去赌电池、温度和欠载。要提高默认值，需用 `--loudness` 在目标
平台重跑 1/2/4/8 线程，并同时跑播放欠载测试；两项缺一不可。

**不做成用户配置项**：用户答不上「响度分析该用几个线程」——要回答它得同时知道内存
带宽、QoS 调度、电池影响与存储介质。将来测出更高的安全默认值也只改后端策略，
不增加设置项。

**不在用户机器跑 benchmark**：它自身要占 CPU（为免打扰而先打扰一次）、结果取决于测
那一刻机器在干什么、且**精确解决了一个不需要精确的问题**。真正知道此刻该给后台任务
多少资源的是操作系统调度器——它知道前台在跑什么、电池还剩多少、机器烫不烫，
QoS 就是把判断交给它的正规途径。`audio/examples/bench_decode.rs --loudness` 是未来调整
默认值的开发期依据，与 `devices`、`play --device` 同类，不进入产品路径。

唯一该给用户的开关是**意图级**而非参数级的：一个「现在全部分析」的显式动作，
对应「插着电、想一次搞定」的场景。首版它只改变队列优先级，不擅自提高并发；待完整负载的
跨平台数据到位后，再决定是否允许该动作临时扩池。

存储介质是我们检测不到的变量：库在网络盘或机械盘上时瓶颈是 I/O，线程多了反因寻道
更慢。与其猜，不如运行时看实际吞吐并自动收敛并发——留待真遇到再做，现在写等于凭空设计。

### 增益应用在管线里，与音量相反

管线顺序里 ReplayGain 在解码之后、重采样之前，而音量在输出回调——两者位置相反，
理由也相反：

- 音量必须即时响应，而管线领先播放约 1.5 秒，放在管线里按下静音要等一秒半；
- ReplayGain 是**每曲固定值**，不需要即时响应；更关键的是**做 gapless 后环形缓冲里
  会同时躺着两首歌的 PCM**，输出回调里那个「当前增益」的全局值必然在边界处把前一首
  的尾巴用后一首的增益放出去。放在管线里则天然对齐——那段 PCM 属于哪首歌，
  写进去时就知道。

由此产生一条排期上的耦合：**先做 ReplayGain 再做 gapless 更省事**，反之则 gapless
的边界处理要额外考虑增益切换。

### 结果的存储与失效

- **键用 `track_id`**：它是「文件大小 + 跳过元数据区的三段内容 blake3」，改标签、
  改文件名、移动文件都不变。响度是**音频内容**的属性，与该 ID 的语义正好对齐——
  分析一次长期复用，用户改元数据不触发重算。
- 每条成功记录只存原始事实：`integrated_lufs`、`true_peak_dbtp` 与状态；**不存最终
  `applied_gain_db`**。目标响度或峰值上限属于播放策略，改策略可立即重算增益，不必重解码。
- 文件带独立 `schema_version`，每条记录带 `analysis_version`。后者至少覆盖锁定的
  `ebur128` 版本、feature、Mode、真峰值算法和声道映射；任一项变化就整体 +1，版本不符
  视为 miss。上游也明确提醒 true peak 可能跨版本变化，不能只靠 `track_id` 长期复用。
- `unmeasurable` / `unsupportedLayout` 是可缓存的确定状态；I/O、解码失败是瞬态错误，不写成
  永久结论。这样既不无限重试静音文件，也不会因一次网络盘掉线永远放弃某首歌。
- **不写回音频文件**：与元数据覆盖层同一条戒律，写标签是破坏性操作，
  不该是「分析响度」的副作用。
- 单独落一份分析结果，性质介于现有两份数据之间：像缓存一样可重建，但重建代价是
  **全库解码一遍**，不能像 `library-cache.json` 那样「损坏就重扫」了事。
- **专辑增益整体后置**：「什么是一张专辑」在本项目里是聚合派生的结论（`aggregate`
  两遍 + 封面指纹合并），合辑尤其麻烦——一张 116 首横跨 6 个艺人目录的合辑，按专辑
  增益归一是对是错属产品判断。分组、跨曲边界与参考实现的交叉验证未完成前，不产出也不
  展示 album gain。

### 分析队列的输入边界（已由扫描器解决）

上述实测暴露的是一个**扫描器**问题，不属于响度归一化，却会直接污染它的输入：
`~/Music` 下的 macOS 包目录被当成普通文件夹递归了。实测除 954 个音乐文件外，
另有 56 个音频躺在 `Logic Pro Library.bundle` 里，`.logicx` 工程包里还有录音片段——
唯一一例解码失败（`too many channels in mask for fmt_ext`）也出自其中。

修复在 `core/src/scan.rs` 的 `collect_files`：walkdir 的 `filter_entry` 在**进入之前**
按目录扩展名剪枝，包内成千上万的素材文件因此根本不会被 stat。实测 `~/Music` 的候选
文件数由 1010 降至 944。响度分析这边不做任何补偿——**在下游过滤上游不该产出的东西，
只会让两处都说不清谁负责**。

`unmeasurable` 因此回到它本来的位置：防的是真静音与极短音频，而不是替扫描器兜底。

### 已知不完美

用户从搜索结果直接跳到一首从未听过的曲目时来不及预取，**当次不归一化**；连续播放
全程准确，只有这种随机跳入是第一次不准、第二次起才准。不要为可选处理给装载硬塞 300 ms
等待：此前同机一首 4 分钟 ALAC 的纯解码就约 400 ms，完整分析只会更慢，固定预算既拖慢
播放又大概率赶不上。播放立即开始，后台结果只服务下一次，是这里明确接受的退化。

## 输出后端

- 能力协商与打开流**分成两个方法**（`negotiate` 只回答「这个请求会落到什么配置上」，
  不碰设备）。链路后半段——环形缓冲容量、重采样比率、位置计数的时基——都要按协商结果
  而不是请求来搭；先 open 再回头调整意味着缓冲刚建好就得推倒重建。
- 采样率**允许协商，声道数不允许**：声道数不符会静默丢声道；采样率不符则插入重采样并
  如实标记。挑选偏好依次是「与源一致 > 源的整数倍 > 高于源的最小者 > 最大者」——
  整数比（44.1 → 88.2）的滤波器比任意比（44.1 → 48）简单，相位与混叠都更好。
- `OutputBackend` trait 首版即定（能力协商 / 启动 / 停止 / 能力上报），WASAPI 独占与
  平台多声道输出后期以新实现插入，不改引擎。trait 必须能表达**声道布局**而不只是声道数，
  否则平台后端接不进来（CPAL 的配置只有声道数，正是这个原因不能承担任何多声道输出）。
- **CPAL 后端只承担立体声**（含单声道上混）。多声道整体走平台原生后端，由系统决定
  空间化还是下混——应用自行下混与自行双耳化是同一类错误，都会把本可被系统空间化的流
  提前拍扁（架构约束「输出后端」）。因此引擎里没有、将来也不会有下混器：
  `mix.rs` 的职责止于立体声路径内的直通与单声道上混。
- 起步实现为 CPAL 共享模式。不得假设设备支持 f32：按设备实际支持的配置协商采样格式
  与采样率；引擎内部全链保持 f32，由输出后端在设备边界完成到协商格式的样本转换，
  转换在回调内进行且无分配。
- 增加 `NullOutput`：供无声卡 CI 与集成测试使用，也是前端 Mock 的行为参照。
- CPAL 的设备热插拔通知跨平台不完整，按架构约束划入平台后端职责，各平台以
  IMMNotificationClient、CoreAudio property listener 等机制补齐。
- macOS 空间输出为 `AVSampleBufferAudioRenderer`（ASBR），实现要点均为实测踩坑：
  - 必须用 `requestMediaDataWhenReady` 驱动。不注册它，`isReadyForMoreMediaData`
    不会转 true，直接 enqueue 等于一帧未送，且不报任何错误。
  - 送入的 `CMSampleBuffer` 需带 `AudioChannelLayoutTag`；12 声道在 macOS 只对应
    `Atmos_7_1_4`，不存在歧义。
  - 队列深度与 CPAL 不同量级（参考约 1 秒，预填约 200 ms）；喂得过浅会被静默丢弃。
  - 欠载用同步器 `setRate(0/1)` 冻结与恢复，非破坏性；不要 flush + 重新预填，
    那会丢弃已缓冲音频并可能锯齿状滑向永久静音。

## 前端接入

- 前端定义 `EngineAdapter` 接口，两个实现按运行环境选择：`TauriEngine`
  （invoke + 事件订阅）与 `MockEngine`（现 `tick()` 占位时钟改造）。浏览器
  `:1420` 的 Playwright 验证流程因此不受引擎接入影响。
- 引擎事件走单通道 tagged union，经 ts-rs 导出到 `src/types/generated/player.ts`；
  `PlaybackProgress.bufferedSec` 由环形缓冲水位换算。
- 每次装载携带不透明的 `trackId` + `loadId`，事件由产生它的引擎代际原样回带；
  不能由外壳读取一个共享“最新曲目”盖章，否则后一条异步命令会把前一代事件盖错。
- 当前有效音量与可选的初始播放位置随 `Load` 一起投递，在打开输出流前生效；不能拆成
  多个无顺序保证的 IPC。初始位置用于播放会话续播：解码器应先定位，再按该位置建立
  输出域位置基准并预缓冲，最后才根据 `autoplay` 解除暂停。若等 `Opened` 跨 IPC 回到
  前端后再补发 `Seek`，输出端已经可能从曲首消费了一段 PCM。
- 错误事件结构对齐架构约束验收条件第 2 条：容器、编码、失败阶段、可展示信息。

## 错误与降级契约

- 曲目中途解码失败：终止该装载代际并发结构化 Error，不再补发自然结束，也不自动跳下一首；
  否则整库格式不支持时会变成一场无声快进。界面保留非阻塞提示，不静默换后端。
- 后续若加入显式重试，以 uid × generation 为键限制次数，避免单曲循环遇上损坏文件形成
  无限错误循环；当前版本不自动重试。
- 端点或格式能力不满足时报明确原因，沿用架构约束：不静默降级。

## 测试策略

`shannon-audio` 与 Tauri 无关，测试全部无头运行：

- **格式矩阵**（`tests/format_matrix.rs`）：语料由 `cargo run -p shannon-audio
  --example make_corpus` 用 ffmpeg 从同一份扫频源转出全部启用格式，验证四件事——
  规格读取（采样率 / 声道数 / 时长）、**无损格式与源逐样本一致**（对齐后误差 < 1e-4
  且偏移为 0）、有损格式整体能量守恒、以及每种格式端到端播完且零欠载。
  另有一条混合格式「歌单」用例：同一个引擎依次播放 44.1k 立体声 → 48k 立体声 →
  单声道 → ALAC，验证**换曲时输出流、环形缓冲与重采样器整套重建**，
  而不是沿用第一首的配置。
  - 语料**不入库**（可复现，且几 MB 二进制进 git 无意义），缺失时用例整体跳过并打印
    生成命令。跳过是有意的取舍：CI 未必装了 ffmpeg，而 PCM 路径已由纯 Rust 语料覆盖。
  - 用 ffmpeg 而非平台工具（如 macOS 的 `afconvert`）：后者只能在一个平台上生成，
    等于把验证能力绑死在开发者的机器上。
- 语料测试：连续正弦波切成两个文件分别编码，断言播放边界处相位连续（误差小于阈值），
  验证 gapless；对应验收条件第 6 条。
- seek 等价测试：任意位置 seek 后的解码输出等于从头解码的对应后缀。
- 欠载测试：慢消费者模拟，断言欠载计数与恢复行为；对应验收条件第 5 条的**后半句**
  （「欠载指标可查询」）。前半句「输出回调不发生阻塞等待或动态分配」见下一节。
- next 替换测试：next 已预解码后修改队列，断言输出不出现旧 next 的样本，且
  TrackChanged 回带新 queueRevision；对应「队列归属与切歌交接」的失效约束。
- 迟到事件测试：越界后才送达新 revision 的 `set_next`，断言引擎仍发出旧 revision
  的 TrackChanged 且 toUid 与实际输出一致；对应“既成事实不丢弃”约束，前端对账
  逻辑以同一场景验证 current 最终与发声曲目一致。
- 命令乱序测试：旧播放链与同链旧 revision 都不能覆盖新 `Load` 原子携带的 next；
  `set_next` 先于对应 `Load` 到达时则必须在建链后生效。
- 撤销 next 后的传输测试：已经预解码的 next 被截断、解码头暂时为空时，当前曲目的
  尾部仍须支持暂停与恢复，不能把 `head = None` 误判成没有播放链。
- 设备切换测试（`NullDevice` 造多端点，无声卡）：换端点后位置接得回去；跨采样率换端点
  后重采样标记与位置时基按新采样率重建；端点用不了（不在 / 给不出立体声）时**不打断
  播放**且不产生换端点事件，空闲时同样当场回报；暂停状态下换端点不擅自开始播放；
  换端点后待接续的下一首仍然接得上。
- AAC / ALAC 等“不能预先承诺 gapless”的格式，以语料测试产出兼容性结论后再更新格式
  范围表，不凭实现推断。
- **启用一个解码器 feature 就要同时把它纳入格式矩阵**。开 flag 是一行的事，
  但那一行是一句承诺；没有语料覆盖的承诺等同于赌它能用，与验收条件第 7 条
  「未经证实的状态不得展示」相悖。
- 测试语料由脚本在开发期生成（属架构约束允许的开发期工具），不提交大体积二进制。

## 实时纪律的机器验证（验收条件第 5 条的实时回调部分）

**状态：已落地**（`audio/tests/realtime_discipline.rs`，10 个用例）。阶段 1 的出口条件是
验收条件第 5 条，以及第 6 条中本阶段已经落地的 gapless、重采样、ReplayGain 与设备切换。
第 6 条的这四项各有用例；其中的**空间后端**尚未实现，归阶段 5 自己验收，不能提前声称覆盖。
第 5 条的两半现在都有证据：「欠载指标可查询」由既有的慢消费者用例覆盖，「不发生动态分配」
由本节的计数分配器夹具机器证明，「不发生阻塞等待」由本节末尾的边界审查逐项对照。

**夹具本身也验过**：往 `render_output_callback` 里临时插一句 `Vec::with_capacity` 后重跑，
10 个用例里 9 个当场失败（剩下那个是计数器自检，不碰生产代码）。只跑通不算数——一个永远
不会红的测试与没有测试等价。

**为什么不推到以后。** 现在只有 CPAL 共享立体声这一条真实输出路径，正适合先把共享填充核心
与 CPAL 自有回调体的夹具建好。阶段 4 的独占输出、阶段 5 的平台原生后端各会增加自己的实时
入口；共享核心的夹具可以复用，但每条新入口仍须补自己的边界验证。现在立规矩，比三条路径
都长出来后再追认便宜。它防的那类故障（负载下偶发的爆音与欠载）听得见、断续、依赖机器
状态，正是「会静默出错的路径必须能无头验证」这条已经用在重采样上的道理。

### 断言什么

测量边界分两层，不能拿共享核心冒充完整回调：

1. `fill_from_ring`（`output/mod.rs`）是消费 ring 的后端共用的填充核心：控制协议、读 PCM、
   增益斜坡、欠载与位置都在这里。
2. CPAL 回调在它外面还做 `begin_callback`、设备延迟换算、scratch 分块、样本格式转换与
   `finish_callback`。这段**我们拥有的回调体**已提取成可直接调用的 `render_output_callback`：
   跨回调保持的那几项（scratch、声道数、斜坡步进、当前增益）收进 `CallbackState`，由后端在
   **建流时**构造一次——它们共享同一条性质「建流时就得备好，回调里一个都不能现造」，散成
   参数时只是签名长，聚起来才看得出它就是被验证的那条不变量。设备时间戳以非装箱闭包传入，
   `begin_callback` 仍发生在读取时间戳之前。真实 CPAL 闭包如今只剩两件事：把设备缓冲与
   时间戳递进去。`NullOutput` 的 worker 也改走同一函数——假设备的价值在于「除了没有声卡，
   其余都一样」，它自己再写一遍 begin/fill/finish 就会悄悄偏离。集成测试测的是这个生产函数，
   不是它的一份复制品。

夹具本身按下面的边界搭：

- **计数分配器**：`#[global_allocator]` 包一层 `System`，在 alloc / dealloc / realloc 三处
  按**线程局部**的开关计数。开关与计数都是线程局部的，否则同一测试二进制里并行跑的其它
  用例会把自己的分配算进来。线程局部量用 `const` 初始化的 `Cell`，回调线程先访问一次再
  武装，避免把 TLS 首次初始化算进被测区间；武装期间不做断言、日志或夹具自身的通信。
- **驱动方式**：测试自己起一条「回调线程」，所有 ring、输出缓冲与 scratch 都在武装前
  分配好；武装开关后按固定轮数调用 `render_output_callback`，主线程只经 ring 的原子协议
  制造 flush / 截断等状态转换。这里要的是**确定地走遍分支**，不是靠真实 tick 与随机系统
  负载赌覆盖；后者只会让 CI 抖动。无需打开设备，也不经过 `NullOutput`，但调用的仍是 CPAL
  生产回调所用的同一段函数，不往生产对象里塞测试钩子。
- **落在独立的集成测试文件**（`audio/tests/realtime_discipline.rs`）：`#[global_allocator]`
  是每个二进制一份，Cargo 给每个 `tests/*.rs` 单独生成二进制，因此它只影响这一个，
  不会波及其余用例，也不会进产物。

### 压力项

验收条件写的是「持续播放、seek 和设备切换」，落到回调这一侧分别是：

| 条件里的说法 | 回调侧实际要走的路径 |
| --- | --- |
| 持续播放 | 生产者跟得上时的常规填充、增益斜坡逐帧收敛 |
| seek | flush 协议（`poll_control` 的请求与回执） |
| 设备切换 | 旧 ring 的常规回调 → paused / rebuffering 下的尾回调 → 控制线程停掉旧流；随后用新 ring 跑首次回调。换端点**不走 flush**，`close/open` 状态机的功能正确性仍由 `tests/playback.rs` 验证 |
| 换曲 | 越过边界帧（`outcome.crossed`，位置改写而非累加） |
| 撤销下一首 | 截断协议（生产端回退写下标前的上限回执） |
| 欠载 | 饿死生产者，走补零与计数分支 |
| 暂停 / 恢复 | 已静音且暂停时的纯零帧路径，与斜坡未收敛时的混合路径 |

每一项都断言武装区间内 alloc / dealloc / realloc 三项均为 0，且控制回执、欠载计数、位置推进
与样本转换仍然正确——只断言「没分配」不够，一个什么都不做的回调也满足它。设备切换这项
只证明切换前后会运行的**回调体**不分配；端点协商、关流、重开与位置接续不在实时线程，继续由
现有设备切换集成测试负责，两类证据不能互相冒充。

### 明确不覆盖的部分

写下来是因为夹具很容易被当成比它实际更强的证明：

- **CPAL 取得设备时间戳的实现，以及 CPAL / 操作系统怎样包裹和调度回调**不在我们的控制内，
  无头夹具照不到；我们拥有的 begin/finish、分块与样本转换则已经纳入上述生产函数，不能再
  留在“靠阅读保证”的灰区。
- **计数分配器只证明动态分配与释放为零，不证明没有阻塞。** 拿锁、文件 I/O 与系统调用都
  可能零分配。第二份证据是边界审查，2026-08-10 逐项过了一遍，武装区间内只有这些：

  | 触碰的东西 | 性质 |
  | --- | --- |
  | `OutputShared` 的 11 个字段 | 全部是 `Atomic*` 的 load / store / fetch_add |
  | `RingConsumer::poll_control` | 只有原子读写，幂等 |
  | `RingConsumer::read` | 原子下标 + 对预分配 `Box<[f32]>` 的 `copy_from_slice` |
  | `settle_marks` | 读定长 `marks` 数组，循环上界是 `MARK_CAPACITY` |
  | `CallbackState.scratch` / `out` | 建流时预分配的切片，只切片不增长 |
  | 增益斜坡、样本转换、延迟换算 | 纯算术 |

  没有锁、没有 I/O、没有系统调用，也没有无界循环。**这份结论会随代码变**：往回调里加东西时
  要重新对一遍这张表，夹具拦不住「零分配的阻塞」。控制协议的活性另由 ring 的有界等待用例保证。
- **后续后端不能搭便车。** `fill_from_ring` 的结果只自动覆盖复用它的共享核心；WASAPI 独占、
  ASBR 与 `ISpatialAudioClient` 各自拥有的实时入口，必须在对应阶段增加同等级的入口测试与
  边界审查，不能凭这一个文件宣称全部后端安全。

### 顺带查出来的一处指标口径问题

**欠载数按 scratch 分块计，不按回调计。** 设备一次要的样本超过 scratch（8192 帧）时回调会被
拆成多块，每块各记一次欠载，于是同一次掉音在不同缓冲大小的设备上得到不同的数字，调小
scratch 也会让这个指标凭空变大——而它要回答的是「实时性够不够」。真机上很少触发（8192 帧
在 48 kHz 上约 170 ms），所以先把行为钉在用例里
（`a_starved_callback_currently_counts_one_underrun_per_chunk`）而**没有顺手改掉**：改的是一个
对外暴露的指标口径，该由维护者定。要改的话，`fill_from_ring` 得改成回报而不是自己累加，
由 `render_output_callback` 每次回调至多记一次。

## 曲库数据库

**现状：已落地**（`core/src/db.rs`，rusqlite 0.39 + `bundled`；应用数据目录下的
`library.db`）。扫描缓存与元数据覆盖层都在里面，0.1 时期的两份 JSON 首次启动时自动搬进来。

- **边界：数据库属于曲库，不是通用存储层。** 只有后端拥有的曲库数据进去。播放会话与
  界面设置仍走 `frontend_state.rs` 的文本槽位——那两份是前端拥有的状态，后端在其中没有
  领域判断可做，给它们建表等于把 schema 的所有权搬错地方。响度分析结果也不进：它在
  `shannon-audio` 里，搬过来要么让解码引擎依赖 SQLite，要么让 `shannon-core` 反向依赖
  音频引擎，两者都比「多一份 JSON」糟。
- **换掉 JSON 是为了三件做不成的事**：改一个字段不必重写整份覆盖层（那份**不可重建**，
  没必要为一次小改动把全部用户劳动置于风险之下）；按 `probe_version` 增量重扫有了索引
  可依；收藏与歌单将来有地方放，且与覆盖层同以曲目 ID 为键、同处一个事务。
- **标量拆列，树存 JSON。** 拆列是为了能查、能按版本增量重扫；具名布局、空间格式与
  探测备注是带 tag 的枚举与数组，摊平成列会让每支持一种新布局就迁移一次表，而戒律要求
  「判不出留空、不归一化」——原样存下的 JSON 正好满足。
- **`track_override` 与 `track` 之间没有外键。** 覆盖记录必须比曲目行活得更久：文件挪走
  后重扫、曲目行消失，用户的修改仍要等在原地，等文件回来靠内容哈希接上。级联删除会把
  这件事悄悄办成「整理一次文件就丢一次修改」。重扫因此只 `replace_cache`，不碰覆盖层。
- **一个文件带来的新耦合要认**：缓存（可重建）与覆盖层（不可重建）现在同处一处，整体
  损坏会一起带走。换来的是事务与 WAL——「写到一半留下半个文件」这个 JSON 时代真实存在
  的失败模式基本消失，而那正是过去最可能弄丢覆盖层的路径。两处补偿：`synchronous=FULL`
  （覆盖层写入多付一次 fsync，用户改元数据的频率以「次/分钟」计，代价可忽略）；确认
  真损坏时按序号保留 `.corrupt` 残骸，不覆盖上一份。只读、锁竞争与磁盘满只报错、不移文件。
- **「读不懂」不等于「坏了」。** 版本高于本程序时走独立的 `SchemaTooNew` 并**原样上报、
  不碰文件**：按损坏处理等于用户装了一次旧版本，整个曲库连同手改的元数据就被改名搬走。
  这条是回归测试抓出来的——最初两者共用一条错误路径。
- **增量重扫已接**（`scan_folders_incremental`）：判据是 stat 的**文件大小 + 修改时间**
  一起比，外加 `probe_version` 未升。不用曲目 ID——ID 是内容哈希，算它就得把文件打开
  读三段，而增量的全部意义正是不碰没变过的文件；两项一起比是因为单看大小会漏掉等长
  改写（改标签常常字节数不变），单看时间会被「复制时保留 mtime」骗过。拿不到修改时间
  时报 0，于是该文件每次都重扫——宁可白干，也不能凭一个拿不到的判据宣称新鲜。schema v5
  加两列，旧记录默认 0，与任何真实 stat 都不相等，各重扫一遍后自愈。有封面指纹但
  缩略图不完整的记录也不复用，会回到媒体文件重新提取；否则上次写入失败或缓存被清理后，
  封面会永久停在占位图。**真机实测**（331 首真实曲库，`warm_cache` 连跑，页缓存已热）：
  首扫 0.67 秒 → 其后每轮 0.01 秒，331/331 全部复用，约 67 倍。局部变化按预期只处理
  变的那些：改一个 mtime → 39/40 复用；新增一个文件 → 40/41 复用；删掉某个封面指纹的
  缩略图 → 共用它的 35 首全部回读媒体文件（6/41 复用）、三档缩略图补齐。`warm_cache`
  示例也随之改走增量路径——它此前停在 `scan_folders` 上，与外壳的 `scan_library` 分叉了，
  于是「预热一次再重扫」这条最该被验证的路径反而永远走不到。
- **收藏与歌单已接**（schema v3 建表、v4 改专辑收藏为成员分组）：曲目 / 专辑 / 歌手 /
  歌单四类收藏与歌单本身都落这里。键的取舍见 `core/src/collections.rs`——**专辑收藏存
  的是成员曲目 ID 的分组快照，不是专辑 ID**（后者由含目录的归组键哈希而来，整理一次
  文件就变）。前端两侧对称：收藏是 `Record<Id, boolean>` 的乐观视图，歌单则保留落盘的
  全部 `trackIds`，界面上那份 `tracks` 只是它按当前曲库水合出的子集——**写回一律以
  `trackIds` 为准**，否则用户改一次歌单名就会悄悄删掉当时查不回本体的那几首。收藏与
  歌单共用一条写入 FIFO 与一个版本号：两者互相引用（新建歌单要接着收藏它、删歌单要
  连带清收藏标记），分成两条队列时一条的回执会带着另一条尚未落库的旧状态盖回界面。
- **未做（明确记下，不假装覆盖）**：数据库损坏目前只写日志，没有界面提示——与 JSON 时代
  一致，但覆盖层与用户攒的收藏、歌单现在都在里面，代价变了，这条迟早要补。

## 曲库扫描选型

- 标签与封面读取用 lofty（覆盖 ID3v2 / Vorbis Comment / MP4 / APE、封面与
  ReplayGain 标签）。
- 扫描期即入库：布局值与布局来源、gapless 元数据（delay/padding）、ReplayGain 标签
  （**若存在**），播放期不再重复解析。实测本机曲库 954 首无一带 ReplayGain 标签，
  故标签只是可选加速路径，响度实际由自带的分析队列测得，见「响度归一化」。
- 满足架构约束进程边界表：扫描不创建子进程。

### 落地过程中的实测发现

1. **Symphonia 0.6 的 `Channels` 已经是「位掩码权威 + `Discrete` 兜底」的建模**，
   与曲库侧的音频规格戒律同构，因此 `ChannelLayout::from_symphonia` 只在
   1 / 2 声道时做推断并标记 `InferredFromCount`，3 声道以上一律不猜。
2. **Symphonia 0.5.5 与 0.6.0 在 workspace 内并存**（`shannon-core` 用前者，
   `shannon-audio` 用后者）。0.6 是 API 大改版，把扫描侧一并升级属于探测器的改动，
   与打通播放链路无关，不放在同一次里做。统一版本是阶段 2 收拾扫描器时的顺带工作。
3. **单声道的判据必须是声道数而非掩码位置**。实测 Symphonia 的 WAV 读取器把单声道
   标为 `FRONT_LEFT`（0x1）而不是 `FRONT_CENTER`（0x4），按掩码比对会把它判成非单声道，
   进而拒播一个本该最简单的文件。
4. **seek 后的位置换算必须走整数**。先转秒再乘采样率会因浮点截断差一帧：定位到第
   43776 帧时 `as_secs_f64()` 得 0.9926530612…，乘回 44100 是 43775.999999，截断即
   43775。差一帧在进度显示上看不出来，却会让「seek 后的解码输出等于从头解码的对应
   后缀」这条不变量失守。
5. **验证 seek 的语料不能用定频正弦**。440 Hz 每 100 帧重复一次相位，位置差整数个周期
   时波形完全重合——上一条的 off-by-one 正是先被定频语料伪装成「误差为零」，换成扫频
   信号后才暴露。位置类断言一律用无周期语料。
6. **seek 引起的重缓冲不计入欠载**。欠载指标要回答的是「实时性够不够」，把用户拖进度条
   的次数混进去就失去了诊断价值。实现上由 `OutputShared::rebuffering` 区分。
7. **默认输出设备不一定支持源采样率**。实测本机默认设备（一个虚拟声卡）只提供
   24 kHz 与 48 kHz，而曲库主力是 44.1 kHz 的 ALAC——原本「不匹配就报错」的行为
   意味着一首歌都放不了。**重采样因此不是阶段 1 的锦上添花而是可用性前提**，
   已提前到本轮实现。蓝牙耳机常见只报 48 kHz，同理。
8. **位置计数一律记输出域的帧**。重采样之后链路里流动的是输出采样率的帧，
   而 `Decoder::seek` 返回的是源域帧位置，两者混用会让进度按比率走偏——
   44.1 → 48 kHz 时快 8.8%，拖到 1:00 显示成 1:05。
9. **重采样路径必须能在无声卡环境验证**。`NullOutput::with_fixed_rate` 模拟
   「只支持单一采样率的设备」正是为此：否则这条路径的正确性只能靠人在特定机器上手动听，
   而它恰恰是最容易出静默错误的一段（比率算反、块边界丢样本、声道错位）。

阶段划分的两处调整依据：

- **阶段 0 的格式主力是 ALAC 而非 FLAC**。实测真实曲库 1362 首中 ALAC 占 87.5%、
  AAC 占 10%、MP3 占 1.8%，FLAC 为 0；FLAC 语料集中在按格式分类的测试素材里。
  因此「能放歌」的端到端验证用 ALAC，「解码正确性」的验证用 FLAC 语料。
  照原表只做 FLAC/MP3/WAV 会出现阶段 0 完成却一首曲库歌曲都放不了的情况。
- **声道布局不能推迟到阶段 5**。布局是交给系统的那份信息本身——多声道输出要附
  `AudioChannelLayoutTag` 一类的标签，系统才知道该空间化还是该怎么下混；
  布局与其来源必须自解码起点即进类型（事后补录代价大）。多声道**输出**在阶段 5，
  但布局**建模**是阶段 0 的出口条件。

## 当前未覆盖

- 均衡器等重型 DSP 的具体设计。
- 歌单的简介编辑与「多久以前」那类相对时间文案：落盘的是时间戳，界面目前只分「今天更新」
  与具体日期两档，`Intl.RelativeTimeFormat` 与配套的分档规则还没引入。

- 导入任务的界面与进度模型细节。
- macOS 对象音频路径与普通路径之间的切歌交接：前者解码器锁定为 AVPlayer，

  都在那个文件里，代价变了。收藏与歌单写失败同样只把界面退回去（红心灭掉、歌单不出现），
  没有文字说明。
